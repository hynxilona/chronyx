Validators

Anyone can follow.
Four can sign.

A follower node syncs the chain, serves RPC and gossips blocks — two commands, no application. A signing slot is different: there are four, they are fixed in genesis, and right now they are handed out by hand.

01

The state of the set

Read this before renting a server.

Chainchronyx-devnet-1
Genesis37808ee8…a083cd
Validators4 · quorum 3
Slot400 ms · one block per validator per 4 slots
Rewardsnone — no inflation, no fees on devnet
Admissionmanual, genesis only

PoW admission is the next milestone. Proofs mine and verify today, but the switch that turns a proof into a scheduled slot is not on main. Until it is, slots are assigned before a devnet reset and announced in the repo first. Do not buy hardware for a slot you have not been offered.

02

Run a follower

Do this first. It is the whole onboarding, and it works today.

shell
chronyx devnet join http://SEED_HOST:8899 --peer SEED_HOST:9000 --dir ./my-node
chronyxd --config ./my-node/node.toml

Check the genesis hash the join prints against the one above. Different hash, different chain — stop and ask before syncing further.

Then verify from your own node instead of trusting anyone:

shell
chronyx -u http://127.0.0.1:8899 cluster health
chronyx -u http://127.0.0.1:8899 cluster supply
chronyx -u http://127.0.0.1:8899 cluster validators
chronyx -u http://127.0.0.1:8899 cluster peers

cluster supply should read 600000000000000000 quanta. It does that only if your node replayed the same ledger as everyone else.

03

What a slot takes

Small box, stable clock, boring operations.

Machine

  • 2 vCPU, 4 GB RAM, 40 GB SSD
  • TCP 9000 reachable from peers
  • 8899 only behind a proxy with rate limits
  • NTP on, or your slots land outside the window

Commitment

  • systemd or a container with Restart=always
  • Identity key backed up, never pasted in an issue
  • One node per identity — double signing has no good story
  • Tell the repo before you take it down for maintenance
04

Apply for a slot

An issue, a keypair, and a proof of work. In that order.

  1. Generate an identity

    shell
    chronyx keypair new --out ./validator.json
chronyx keypair show ./validator.json

    Publish only the public key. The secret stays on the box.

  2. Mine the admission proof

    shell
    chronyx pow mine --difficulty 20
chronyx pow verify <proof-hex>

    Difficulty 20 is about a million hashes. It proves the box can do the work the post-v1 admission will require.

  3. Open the issue

    New issue titled validator application: <handle>. Include region, specs, uptime commitment, public key and proof. Names in cluster validators are opt-in.

  4. Wait for the reset

    Slots for the current devnet are full. Applications are queued for the next reset, and everyone in the queue gets pinged before it happens — no surprises, no silent wipe.

05

What operators get

No tokens. Something better than a promise.

Devnet

A named slot

Your handle in cluster validators, your name in the repo, and the first look at every design change before it ships.

Mainnet

Bootstrap list

The plan puts 15% of supply behind the operators who were actually up during devnet. Locked, vested, not sold — and not distributed yet.

Either

A say in what breaks

Operators see the failure modes first. That is the group worth being in when the protocol is still soft enough to change.
