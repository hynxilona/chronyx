How it works

One block,
four hundred milliseconds.

A slot is the unit of time. Eight PoH ticks fit inside it, one leader fills it, and a quorum signs it. Everything else — accounts, transfers, gossip — hangs off that rhythm.

01

The slot, end to end

What actually happens between two blocks.

  1. The leader is already known

    Validators are ordered in genesis. Slot n belongs to validator n mod 4. No election, no auction, no waiting to find out who is allowed to produce.

  2. Eight ticks establish the order

    Each tick is SHA-256(previous_hash), 50 ms apart. The hash chain proves the leader could not have produced tick 7 before tick 6, and gives every node the same sequence for the transactions inside the slot.

  3. Transactions apply in that order

    A transfer carries sender, receiver, amount, nonce and an Ed25519 signature. Nonces make replays fail; the amount is checked against the balance; the state update is atomic. There is no VM and nothing to re-execute twice.

  4. The block is sealed and signed

    Header holds the parent hash, slot, merkle root over transactions, the PoH hash at the end of the slot, and the leader's signature.

  5. Quorum makes it final

    Three of four validators sign the block. There is no reorg window after that: the next leader builds on it or the chain stalls. Stalling is visible, which is the point.

  6. Gossip carries it

    Plain TCP. Peers exchange height on connect, pull the gap with GetBlocks, then receive live blocks as they seal. A node that was offline for an hour replays the ledger from disk and catches up the same way.

02

Touch the clock

This is the real construction, running in your browser. Eight ticks, eight hashes.

poh_chain · sha-256

    Each row is the hash of the row above it. Nothing else goes in.

    The chain in the node does the same thing, except each tick is hashed with the slot's transaction data folded in and stored in the ledger.

    03

    The door needs work

    PoW is how a stranger earns a validator slot without buying one.

    Mine a proof against a difficulty target:

    shell
    chronyx pow mine --difficulty 20
chronyx pow verify <proof-hex>

    Difficulty 20 is roughly a million hashes — seconds on a laptop, minutes on a small VPS. It is a cost, not a lottery: the proof is checked in microseconds and cannot be reused.

    What the proof is bound to:

    IdentityEd25519 pubkey
    Challengeseed + identity
    Targetleading zero bits
    Verificationone SHA-256

    v1 status. Proofs mine and verify today. Automatic admission is not on main yet — validators are written into genesis, and the application process is in Validators.

    Where the code is

    No generated clients, no framework, no magic.

    05

    What v1 does not do

    Said plainly, so nobody has to discover it the hard way.

    • No dynamic validator admission — genesis only
    • No fees and no rewards: devnet has no economy
    • No light clients or proofs of state
    • No explorer, no indexer, no wallet UI
    • No QUIC, no gossip encryption
    • No audit. Not one line of it

    PoH orders. PoA finalizes. PoW admits. A Rust chain with a fixed supply and no framework to hide behind.
